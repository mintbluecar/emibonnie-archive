# Architecture

This document is copied from the engine's implementation plan ("Architecture and code rules" and the file structure) so it stays next to the code it governs.

## Architecture and code rules

A reviewer rejects any task that breaks these rules.

```
api/index.js             the ONLY Vercel function: builds deps per request, dispatches via src/routes/index.js
src/routes/              one module per endpoint: export const route = { method, path, cache, run({ query, body, params, user }, deps) }
src/http/                router, handler wrapper (errors, cache headers, Origin check for writes), query parsing, contracts.js (response typedefs)
src/services/            orchestration across repos/sources/kinds (ingest, search, hub views, seedFromSite). Never names a kind.
src/kinds/<kind>/        one folder per item kind: index.js (defineKind), domain.js (pure), repo.js, presenter.js, search.js
src/kinds/_registry.js   GENERATED by the build from the folder list (static imports)
src/repo/                SQL for core tables, one module per table group
src/sources/             network access to external sources (registry in index.js); offlineFetch.js for seeds/tests
src/db/                  client (per-request pool, date parser, transactions with actor), migrations runner, migrations/
src/site/                settings schema/validation, regions.js (Vercel regions), copy, generated.js (GENERATED: static import of site config)
src/domain/              PURE: no I/O, no clock, no imports from other layers
src/pages.js             the one list of page routes (rewrites, reserved kind prefixes)
public/js/core|components|pages|state|kinds/<kind>/   browser code (no src/ imports); kinds/_registry.js GENERATED
scripts/                 build, dev, setup, migrate, doctor, init-site, seed-dev, add, new (scaffolder + templates/)
site/                    a site's own folder (gitignored in the template); examples/solluna/ is the template example
```

**Rules:**
1. **One source of truth for each fact:**
   - Visibility: `visibleItem()` in `src/repo/visibility.js`.
   - Engine constants: `src/domain/constants.js`.
   - Fandom values: `site/site.json`.
   - Response shapes: `src/http/contracts.js`.
   - Wording: `src/site/copyDefaults.json`, with keys namespaced (`translation.showN`). Each kind's own copy lives in `src/kinds/<k>/copy.json`, merged at build.
   - A test checks that constants match the SQL check constraints and lookup rows: `KINDS` ↔ `item_kinds`, `ROLES` ↔ the `speaker_role` domain, `PLACEMENTS`, `REVIEW_STATES`.
2. **No god modules.**
   - ESLint: `max-lines` 200 (blank lines and comments skipped), `max-lines-per-function` 50, `complexity` 10, `max-params` 4. Tests are exempt.
   - Typedefs live next to the code that produces them, not in one types file.
3. **Enforced layers.**
   - `no-restricted-imports` per layer:
     - `domain` imports nothing.
     - `repo` may not import services, sources, http, routes or kinds.
     - `services` may not import http or routes.
     - `routes` may not import repo or db directly.
     - `kinds/*/domain.js` follows the domain rules.
   - `import/no-cycle` is an error.
4. **Dependency injection.**
   - `deps = { db, fetchImpl, now, site }`, built per request by `withDeps()` and closed in `finally`.
   - No module-level mutable state, except memoised pure lookups keyed by the `db` instance.
5. **Kinds are plugins.** Adding a kind (`npm run new kind <k>`) means:
   - a new `src/kinds/<k>/` folder
   - a migration in `src/db/migrations/` (its `<k>_items` table with a composite FK to `items (id, kind)`, plus a row in `item_kinds`)
   - a `public/js/kinds/<k>/` folder, and its tests under `test/kinds/<k>/`

   Nothing else changes, apart from what the build regenerates into gitignored files (`vercel.json`'s item-page rewrite, bundle hashes in `public/*.html`). `setup` and a test check that the registry matches the `item_kinds` rows; `test/kinds/scaffoldedKind.test.js` proves the whole path in a temp copy. Core tests must take the set of kinds, migrations and routes from their sources (the registry, the migrations folder, `src/pages.js`), never pin today's list.
6. **Schema changes are new migrations.**
   - Engine migrations live in `src/db/migrations/NNN_*.sql`. A site's own migrations live in `site/migrations/`, tracked separately.
   - Migrations are checksummed: editing an applied one fails.
   - Use expand/contract: never drop or rename in the same release that adds the replacement.
7. **Parameterised SQL only.** The actor is set with `set_config('app.actor', $1, true)`.
8. **Type-checked JS.** Every file starts with `// @ts-check`. `npm run check` runs tsc, eslint, and the cycle check.
9. **Database conventions** ([ADR 0006](decisions/0006-data-model-conventions.md)):
   - Entity tables share `id` (identity), `created_at/by`, `updated_at/by`, `deleted_at/by` and `meta`; join tables carry `created_at/by` only.
   - Soft delete only (erasure scripts and join-table rewrites excepted).
   - Writes go through `db.transaction(fn, { actor })`; triggers stamp the actor and write a diff-only `audit_log`, and refuse writes with no actor.
   - `meta` is display-only; growing value sets are text-coded lookup rows, closed sets are checks.
   - Slugs are unique forever; other unique keys are partial on `deleted_at is null`.
   - Moments are `timestamptz`, days are `date` in the site's time zone, read back as `'YYYY-MM-DD'`.
10. **Naming:**
    - Files are `camelCase.js`. Functions are verbs. Pure transforms are named after what they return.
    - SQL is `snake_case`. Repos map rows to camelCase.

## Routing on Vercel

There is one function, `api/index.js`, and the build writes every `vercel.json` rewrite that reaches it with an **unnamed** source and the destination exactly `/api`: `/api/(.*)`, then each link-preview page (`/e/(.*)`, and `<urlPrefix>(.*)` per kind, e.g. `/t/(.*)`). Static pages rewrite to their file the same way (`/p/(.*)` to `/person.html`).

- **Why unnamed:** a named param in a source is added to the request's query string (`/t/:id` arrives as `/t/123?id=123`; [Vercel's rewrites doc](https://vercel.com/docs/routing/rewrites): "This converts a request like /resize/800/600 to /api/sharp?width=800&height=600"), and the handler refuses unknown query params. A catch-all file name (`api/[...route].js`) does the same with its segment, and only matches one level deep.
- **Why `/api`:** the function sees the original request URL, not the rewrite's destination, so the route table matches `/api/home` and `/t/:sourceId` directly. `src/pages.js` (a page's `meta`) and the kinds registry (`urlPrefix`) decide which page paths have meta; `src/routes/meta.js` builds the routes and `src/routes/index.js` the rewrites from them.
- `test/site/build.test.js` fails on a named source or a function rewrite to anything but `/api`. `scripts/dev.js` routes the same way (a rewrite to `/api` calls the handler with the original URL) and refuses a named source, but it can't reproduce Vercel's own quirks, so the first preview deploy must check `/api/home` and `/t/<id>` (`docs/start-your-own.md`, step 6).
