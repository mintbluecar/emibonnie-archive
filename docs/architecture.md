# Architecture

This document is copied from the engine's implementation plan ("Architecture and code rules" and the file structure) so it stays next to the code it governs.

## Architecture and code rules

A reviewer rejects any task that breaks these rules.

```
api/index.js             the ONLY Vercel function: builds deps per request, dispatches via src/routes/index.js
src/routes/              one module per endpoint: export const route = { method, path, cache, run({ query, body, params, user }, deps) }
src/http/                router, handler wrapper (errors, cache headers, Origin check for writes), query parsing, contracts.js (response typedefs)
src/services/            orchestration across repos/sources/kinds (ingest, search, hub views, seedFromSite). Never names a kind.
src/kinds/<kind>/        one folder per item kind: index.js (defineKind), domain.js (pure), repo.js, presenter.js, search.js
src/kinds/_registry.js   GENERATED by the build from the folder list (static imports)
src/repo/                SQL for core tables, one module per table group
src/sources/             network access to external sources (registry in index.js); offlineFetch.js for seeds/tests
src/db/                  client (per-request pool, date parser, transactions with actor), migrations runner, migrations/
src/site/                settings schema/validation, regions.js (Vercel regions), copy, generated.js (GENERATED: static import of site config)
src/domain/              PURE: no I/O, no clock, no imports from other layers
src/pages.js             the one list of page routes and redirects (rewrites, vercel.json redirects, reserved kind prefixes)
public/js/core|components|pages|state|kinds/<kind>/   browser code (no src/ imports); kinds/_registry.js GENERATED
scripts/                 build, dev, setup, migrate, doctor, init-site, seed-dev, add, remap, new (scaffolder + templates/)
site/                    a site's own folder (gitignored in the template); examples/solluna/ is the template example
```

**Rules:**
1. **One source of truth for each fact:**
   - Visibility: `visibleItem()` in `src/repo/visibility.js`.
   - Engine constants: `src/domain/constants.js`.
   - Fandom values: `site/site.json`.
   - Response shapes: `src/http/contracts.js`.
   - Wording: `src/site/copyDefaults.json`, with keys namespaced (`translation.showN`). Each kind's own copy lives in `src/kinds/<k>/copy.json`, merged at build.
   - A test checks that constants match the SQL check constraints and lookup rows: `KINDS` ↔ `item_kinds`, `ROLES` ↔ the `speaker_role` domain, `PLACEMENTS`, `REVIEW_STATES`.
2. **No god modules.**
   - ESLint: `max-lines` 200 (blank lines and comments skipped), `max-lines-per-function` 50, `complexity` 10, `max-params` 4. Tests are exempt.
   - Typedefs live next to the code that produces them, not in one types file.
3. **Enforced layers.**
   - `no-restricted-imports` per layer:
     - `domain` imports nothing.
     - `repo` may not import services, sources, http, routes or kinds.
     - `services` may not import http or routes.
     - `routes` may not import repo or db directly.
     - `kinds/*/domain.js` follows the domain rules.
   - `import/no-cycle` is an error.
4. **Dependency injection.**
   - `deps = { db, fetchImpl, now, site }`, built per request by `withDeps()` and closed in `finally`.
   - No module-level mutable state, except memoised pure lookups keyed by the `db` instance.
5. **Kinds are plugins.** Adding a kind (`npm run new kind <k>`) means:
   - a new `src/kinds/<k>/` folder
   - a migration in `src/db/migrations/` (its `<k>_items` table with a composite FK to `items (id, kind)`, plus a row in `item_kinds`)
   - a `public/js/kinds/<k>/` folder, and its tests under `test/kinds/<k>/`

   Nothing else changes, apart from what the build regenerates into gitignored files (`vercel.json`'s item-page rewrite, bundle hashes in `public/*.html`). `setup` and a test check that the registry matches the `item_kinds` rows; `test/kinds/scaffoldedKind.test.js` proves the whole path in a temp copy. Core tests must take the set of kinds, migrations and routes from their sources (the registry, the migrations folder, `src/pages.js`), never pin today's list.
6. **Schema changes are new migrations.**
   - Engine migrations live in `src/db/migrations/NNN_*.sql`. A site's own migrations live in `site/migrations/`, tracked separately.
   - Migrations are checksummed: editing an applied one fails.
   - Use expand/contract: never drop or rename in the same release that adds the replacement.
7. **Parameterised SQL only.** The actor is set with `set_config('app.actor', $1, true)`.
8. **Type-checked JS.** Every file starts with `// @ts-check`. `npm run check` runs tsc, eslint, and the cycle check.
9. **Database conventions** ([ADR 0006](decisions/0006-data-model-conventions.md)):
   - Entity tables share `id` (identity), `created_at/by`, `updated_at/by`, `deleted_at/by` and `meta`; join tables carry `created_at/by` only.
   - Soft delete only (erasure scripts and join-table rewrites excepted).
   - Writes go through `db.transaction(fn, { actor })`; triggers stamp the actor and write a diff-only `audit_log`, and refuse writes with no actor.
   - `meta` is display-only; growing value sets are text-coded lookup rows, closed sets are checks.
   - Slugs are unique forever; other unique keys are partial on `deleted_at is null`.
   - Moments are `timestamptz`, days are `date` in the site's time zone, read back as `'YYYY-MM-DD'`.
10. **Naming:**
    - Files are `camelCase.js`. Functions are verbs. Pure transforms are named after what they return.
    - SQL is `snake_case`. Repos map rows to camelCase.

## Routing on Vercel

There is one function, `api/index.js`, and the build writes every `vercel.json` rewrite that reaches it with an **unnamed** source and the destination exactly `/api`: `/api/(.*)`, then each link-preview page (`/e/(.*)`, and `<urlPrefix>(.*)` per kind, e.g. `/t/(.*)`). Static pages rewrite to their file the same way (`/p/(.*)` to `/person.html`).

- **Why unnamed:** a named param in a source is added to the request's query string (`/t/:id` arrives as `/t/123?id=123`; [Vercel's rewrites doc](https://vercel.com/docs/routing/rewrites): "This converts a request like /resize/800/600 to /api/sharp?width=800&height=600"), and the handler refuses unknown query params. A catch-all file name (`api/[...route].js`) does the same with its segment, and only matches one level deep.
- **Why `/api`:** the function sees the original request URL, not the rewrite's destination, so the route table matches `/api/home` and `/t/:sourceId` directly. `src/pages.js` (a page's `meta`) and the kinds registry (`urlPrefix`) decide which page paths have meta; `src/routes/meta.js` builds the routes and `src/routes/index.js` the rewrites from them.
- **Redirects (v0.1.4):** `src/pages.js`'s `redirects` (today only `/search` → `/`, 308) go into `vercel.json`'s `redirects` as plain-path sources. Vercel runs `redirects` before `rewrites` ([vercel.json doc](https://vercel.com/docs/project-configuration/vercel-json)) and passes the request's query string on to the destination by default ([Vercel KB](https://vercel.com/kb/guide/how-do-i-perform-vercel-redirects-based-on-query-strings): "By default, all query strings that are found in the source path will be passed to the destination path"), so `/search?q=x` lands on `/?q=x`. `scripts/dev.js` answers them the same way, appending the query itself.
- `test/site/build.test.js` fails on a named source or a function rewrite to anything but `/api`. `scripts/dev.js` routes the same way (a rewrite to `/api` calls the handler with the original URL) and refuses a named source, but it can't reproduce Vercel's own quirks, so the first preview deploy must check `/api/home` and `/t/<id>` (`docs/start-your-own.md`, step 6).

## Search happens in place (v0.1.4)

There is no search page. Home is the search, and the event, person and translator pages each search within themselves (spec, "Search happens in place"). One controller does it for all four:

- `public/js/components/inlineSearch.js`: `prepare()` reads the page URL's query before the first paint (so a `?q=` link never flashes the list), `bind()` wires the header's box and filter button, the chips and "more" once each, loads `/api/filters`, and fetches results when the URL already holds a search. `commit()` applies a new state: `history.replaceState` on the page's own path, the chips and placeholder, then either the page's own list (no fetch) or fresh results. A sequence number drops any response a newer one has overtaken. Nothing here navigates and nothing autofocuses.
- `inlineSearchView.js` (pure markup): a page places `filtersSlot` (the active-filter chips, right under the box), then its own head, then `region(ctx, list)`, which wraps the page's list and the results area and shows one of them. `headerProps` gives the header its search row (`header.render({ search })`); a page without it has no box, only the phone bar's icon home.
- `inlineSearchSheet.js` opens the shared `filterSheet.js` on a fresh node each time.
- `public/js/state/searchScope.js` (pure): a scoped page's own filter (`event`, one of `people`, or `account`) is preset and implied by the path, so the URL reads `/e/x?q=hi`; removing its chip writes `scope=all` so a reload keeps it removed. `viewOf()` decides what shows: the page's own `list` (nothing typed, no filter beyond the page's own), `results`, or a `hint` to type when a scoped page's own filter was removed and nothing else is set. Leaving results for the list or hint empties `.c-search` and forgets its data; a search in flight marks it `aria-busy`. One `role="status"` live region, outside `.c-search`, announces each result count, "no results" or the error.
- The server API (`/api/search`) is unchanged. The meta routes (`query: null`) never parse their query, so a page URL with repeated params (`?people=1&people=2`) can't 400.

## Sign-in, adding and editing (v0.2.0)

Visitors sign in with X or Google (`/me`); a signed-in member adds entries (`/add`) and edits them (`/edit/:kind/:sourceId`); the owner also sees and reverts edit history.

- **Sign-in is hand-written OAuth**, not an auth library (no adapter over the database). X uses PKCE (`src/services/xSignIn.js`); Google uses an `openid` code exchange with a nonce and checks the id token's audience and expiry (`src/services/googleSignIn.js`). The state a flow carries between its start and callback is HMAC-signed with `AUTH_SECRET` and expires after 10 minutes (`src/services/oauthState.js`). The start routes are rate-limited by address (`docs/limits.md`).
- **Sessions** are a `sid` cookie with a row in `sessions`, so sign-out and sign-out everywhere revoke a session server-side. `src/services/session.js` reads the cookie; `/api/me`, `/api/me/name`, `/api/me/added` and `/api/me/delete` are the me page's API.
- **Adding** is `POST /api/add/preview` (a dry run that writes nothing) and then `POST /api/add`, both in `src/services/addFlow.js` over the same `ingestItem` the CLI uses. A member's add is visible at once unless the owner has turned approval on. Ingest allows unmapped markers here, so an entry can be saved before its speakers are chosen, and a member may only pick existing categories and clients.
- **Editing** is `POST /api/item/:kind/:sourceId/edit`: it changes only the fields sent, writes one `item_edits` row with the before and after, and the owner reverts any entry with `…/edits/:editId/revert`. Line fixes are stored as a list of fixes, not as edited text, so a refreshed part keeps its speaker map and loses only its line fixes.
- **The item page is private for signed-in visitors.** Its editor controls differ per user, so `/api/item/…` answers `private, no-store` to them. Signed-out readers keep the cached page.
- **The front end shares one set of rules.** The add and edit pages render the same components (`public/js/components/addLink.js`, `addDetails.js`, `speakerStep.js`, `lineFixSheet.js`, `personPicker.js`), with markup in `addView.js` and `editView.js`. `public/js/state/addState.js` is the only place that turns the choices into request bodies, so the two pages can't disagree about what a save sends. `pages/add.js` and `pages/edit.js` own state, the network and the 300 ms re-preview.
- **Dev only:** `DEV_SIGN_IN=1` enables `POST /api/auth/dev` (refused whenever `VERCEL` is set). The browser tests run the dev server against offline fixtures with `INGEST_FIXTURES_DIR`, which `api/index.js` ignores on Vercel.


## Translators, reports and the owner (v0.3.0)

A translator recognised by an X sign-in controls their own work; anyone can report a page; the owner gets the minimum moderation tools until Plan 3's admin.

- **`/api/me/translations`** (signed in, `private, no-store`) lists every item credited to the caller's linked X accounts, in any review state, with removed rows flagged for restore (`src/services/translator.js`). `…/remove` and `…/restore` take 1–50 `{ kind, sourceId }` entries and are all-or-nothing; only `removed_by_account` is a translator's to undo. `…/opt-out` and `…/opt-in` set `accounts.opted_out_at` for every linked account (`purgeAccount` afterwards); nothing is soft-deleted, so opting back in restores exactly those entries.
- **Reports** are `POST /api/reports` (no sign-in, rate-limited by hashed address): a target must be a visible item or event right now, so a hidden one is a 404 (`src/services/reports.js`).
- **The owner section** is `GET /api/owner` plus `POST /api/owner/{approval,items/:kind/:sourceId/review,reports/:id/hide|restore|dismiss,users/block|unblock,sign-in-alert/dismiss}` (`src/services/owner.js`, `ownerUsers.js`), all `requireOwner`. Approving publishes; rejecting sets `review_state = 'rejected'`, which the public visibility rule already hides. Hiding an event reuses 1a's `softDeleteEvent` (its items move to unsorted and stay archived), so restoring the event row does not re-place them.
- **Cache tags and purging.** Public GETs set `Vercel-Cache-Tag` (`src/domain/cacheTags.js`, `src/http/cacheTags.js`): `home`, `search`, `item:<id>`, `event:<slug>`, `person:<id>`, `account:<handle>`. A write that changes a public page calls `purgeItem`/`purgeAccount`/`purgeTags` (`src/services/cache.js`) after its transaction, deferred through `waitUntil`, and Vercel's `invalidateByTag` marks the cached copies stale. People are tagged by numeric id so a handle change can't orphan a page. Off Vercel it is a no-op, and a purge failure is logged, never thrown.
- **The me page** composes the account block (`pages/meAccount.js`), the translator component (`components/meTranslations.js`), the shared panels (`components/meSections.js`) and the owner section (`components/ownerSection.js`). The report dialog is `components/reportForm.js`, used by the item footer and the event page.
